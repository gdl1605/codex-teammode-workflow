# 普通开发工作流

> 最后更新时间：2026-11-05
> 适用范围：未显式启用 Team Loop 的开发规划（包括仅产出计划）、维护及有实质内容的文档修改
> 本文主职责：定义主 agent 的规划、需求追问、实现及独立核验闭环
> 推荐下一跳：`independent-evaluator.md`

## 职责和适用边界

普通工作流由主 agent 直接规划、实现、运行必要验证，并调度一个只读 evaluator subagent。它不启用 Team Loop 的 Leader / planner / generator / scout 分工，也不禁止主 agent 改文件。

用户明确要求 Team Loop 时，改用 `team-loop.md`，不再叠加一次普通 evaluator。仅要求独立核验、使用 evaluator 或讨论工作流，不等于要求 Team Loop。

仅产出计划的任务同样执行下文“正式计划交付前的关键取舍澄清”，交付计划后结束，不自动进入实现和实现后核验。单纯问答、没有方案交付的只读调查不自动进入开发循环；安装、升级及显式调用的 skill 沿各自授权和协议执行。用户或目标项目对改动、subagent、运行环境的明确限制仍然有效。没有独立 subagent 能力时如实说明实际自查范围，不把自查称为独立核验。

## 流程

```text
核对原要求、既有合同与当前实现
→ 形成与任务规模相称的草案
→ 核对关键取舍的来源；Grill-me 追问尚未确认的选择
→ 将决定依据和用户回答写回同一份正式计划
  ├─ 仅规划：交付后结束
  └─ 已授权实现：按计划和原授权实施
     → 运行直接受影响的必要验证
     → fresh evaluator 独立核验
     → 主 agent 修复有依据的缺口；争议交用户裁决
     → 报告实际完成、核验范围及残留事项
```

草案和核验材料可直接写在当前聊天；已有计划时更新原计划。小改动不要求新文件、独立 Spec、Claim ID、状态机或固定输出 schema。

草案可以先提出建议，但不能把仍待选择的内容当成已确认决定交付。用户要求先看草案、暂不问问题时，按其要求提供待确认草案，保留未决项；不把这次展示当成对这些选择的批准。

## 先分清事实、决定与假设

对会影响方案、行为、阻塞判定或完成声明的关键断言，保持以下区别：

| 类型 | 含义与依据 |
|---|---|
| 已核实事实 | 由实际读到的 current code、原始记录或实际验证结果支持；写明证据能证明的范围 |
| 用户决定 / 既有合同 | 规定应该做什么，附用户原话或规范主落点；不能从当前代码反推授权 |
| agent 假设 / 推断 / 建议 | 说明依据和仍未证实的部分；重复出现在计划、代码、测试或总结中不会使它成为事实 |
| 待核实 | 证据不足，或来源冲突尚不能消解；先查可获得的真实来源 |

只追溯影响本次决策的断言，不要求为每句文字建台账。明确的普通实现细节由 agent 在授权范围内决定，不冒充用户决定，也不逐项要求用户批准。

代码用于证明当前实现；用户明确要求与有效合同用于确定目标。源码存在、测试通过、运行加载、实际消费、业务成功分别需要相应证据，不能逐级自动推导。测试与实现如果共享同一个无依据假设，测试通过不能证明这个假设成立。

## Grill-me：正式计划交付前的关键取舍澄清

本包内置此澄清步骤，不依赖安装外部同名 skill，也不假定该 skill 已执行。

- 先查现有代码、合同与记录。事实查证由 agent 完成，不把可以自行查到的事实变成用户问卷。
- 每次交付正式方案或计划前，包括只规划、不实现时，都核对会改变用户可见行为、算法含义、职责、输入范围、资源成本、停止条件或验收口径的关键取舍。先区分当前实现事实、用户决定 / 有效合同、agent 建议和待核实事项，不能因为 agent 已选了默认方案就判断没有未决项。
- 已有明确决定的直接沿用，并指出相关用户原话或合同条款。用户已明确委托 agent 决定该类取舍时，在委托范围内作出选择并说明依据，不重复请求授权。未改变上述边界的普通实现细节由 agent 自行决定。
- 仍是 agent 提议、又会改变上述结果的选择，先向用户提出问题，说明选项的具体后果和建议，等回答后再把依赖该选择的内容定为正式计划。“建议”“默认”“首版”“暂不支持”等措辞只标明提议性质，不代表该选择已被用户确认。用户说“规划一下”不自动确认方案中新提出的关键取舍。
- 正式计划简短交代关键取舍的具体决定及出处；若无需追问，说明哪些已有要求、合同或明确委托覆盖了这些选择，不能只写“没有未决项”。不要求逐句建表、固定字段或额外审批工件。
- 互不依赖的问题同一轮问；依赖前一个答案的问题在答案确定后再问。不设固定轮数或必须问满的问题数。事实尚未查清时先由 agent 查证，不能用假定事实迫使用户作选择。
- 用户的回答和已核对的决定依据回写同一份计划 / 原有 Spec。保留原要求及后续修改的出处，不能只留 agent 对原话的概括。
- 只有确需用户选择的部分等待回答；其他已授权且不依赖答案的工作继续。澄清结束不自动新增一次整份计划批准，沿用本任务原有授权；用户要求先批准计划时遵守该要求。
- 实现中若发现需要改变已确认行为或超出授权，明确提出该项变化，不能用“实现细化”静默覆盖。

例如，已核实“当前接口没有取消能力”时，这是实现事实；“本次只等待在途请求结束、不补取消能力”是交付范围选择。前者不能单独证明后者已获确认。应先查是否有既有决定或明确委托；没有时，在定稿前询问本次退出处理是否包含取消能力，而不是选好“首版暂不支持”后跳过追问。

不得为设计完整而自行添加超时、重试、数量上限、校验、兼容路径或失败条件。只有用户要求、既有合同、外部协议或已复现故障可以定义相应约束；诊断信号触发后应核对真实状态，不能自动升级成失败或停止依据。

## 如何给 evaluator 交任务

主 agent 完成实现和必要验证后，创建全新上下文的只读 evaluator，按 `independent-evaluator.md` 发送 Review Request。支持关闭历史继承的工具应关闭继承，只发送裁剪后的请求，不带完整实现对话。

审查范围从三处形成：**原要求和确认后的决定规定应做什么；实际 diff 暴露做了什么；真实调用链确定影响谁。** 主 agent 给出的关注点只是起点，不能限制 evaluator 发现同一改动影响到的遗漏。不要只发“帮我看看代码”或“确认计划已完成”。

请求包含以下信息；没有的项如实标注，不为填满模板编造内容：

```md
## Review Request

- 原始要求及来源：相关用户原话、后续纠正、有效合同的准确位置
- 已确认的决定 / 待核实假设：分别列出；计划中关键取舍的原决定、用户回答或明确委托及其来源，已有计划或 Spec 的位置
- 本次修改范围：实际 diff / 变更文件；已有脏项和本次变更的界线
- 预期行为及不能改变的边界：每项要求对应什么可观察结果
- 影响路径：已知生产入口、消费者及拟替换的旧路径
- 验证证据：实际运行的命令、结果、未覆盖范围；仅建议运行的须标明未执行
- 完成声明：实现 agent 准备向用户声称什么；证据目前达到哪一层
- 读取与操作授权：必要文件及原始记录，禁止修改 / 外部操作范围
- evaluator 规则：docs/workflow/independent-evaluator.md
```

不把审查请求写成第二套业务规范。原要求、计划、代码冲突时按断言类型追溯来源，不默认以“最新生成的总结”为准。

## 缺口、补证与争议的回流

- 明确违反要求、遗漏真实消费者、或把假设写成事实的项，evaluator 直接报告给主 agent。主 agent 在已有授权内修复，无需为每个确定缺口再次请用户批准；修复实际行为和错误声明，不能改低验收要求来消除问题。
- 可查证的事实缺口，由 evaluator 在读取授权内补查，或交主 agent 补证。暂时没有证据不等于事实为假、业务失败或用户必须裁决。
- 需要改变用户决定、有效合同相互冲突或真正存在业务取舍时，保留争议，向用户提供原条款、实际行为、不同选择的影响及建议。双方推断都不得写成裁决后的事实；其他不受影响的工作继续。
- 修复后用 fresh evaluator 只复核原发现、实际修复及直接受影响路径；仅有新增改动或未解问题时扩大范围，不反复全量审查。不设置自创的轮数、时限或检查数量作为失败门槛。
- 达到既有验收要求后收口。evaluator 不能以个人偏好添加阻塞项，也不能代表用户宣布验收或发布。

## 验证和文档

复用现有检查，迭代只运行直接受影响的最小集合。只有新增可观察行为且现有检查无法覆盖、又有独立判断标准时才新增持久测试；不为每次修改建立 validation harness。

主 agent 按 `docs-maintenance.md` 更新本次真正影响的文档主落点，evaluator 核验其事实与假设表述。普通核验不自动触发可选的 `$docs-review`，不代替其独立协议。

最终说明修改结果、实际验证、独立核验范围、未核实事项和待用户裁决项。没有做过或证据未达到的层次，不声称已经完成。
